# Assumptions Audit Log

## Fixed Assumptions

### 1. Committee Code Map was Static (Fixed: dynamic from API)
- **What it assumed:** The 25 committee codes (H01-H24, S01-S13) never change
- **How it broke:** New committees could be created, existing ones renamed or merged between sessions
- **Fix:** Rebuilt from Committee API at runtime with static fallback + drift alerting

### 2. LOCAL_LEXICON was Hardcoded (Fixed: derived from API)
- **What it assumed:** Committee name aliases are stable across sessions
- **How it broke:** Committee names change (e.g., "Courts of Justice" was H02 in old map, is actually H08)
- **Fix:** Auto-generated from Committee API names, splitting on commas/ands

### 3. Parent Fallback Used startswith Heuristic (Fixed: ParentCommitteeID)
- **What it assumed:** Subcommittee names always start with parent committee name
- **How it broke:** Could match unrelated committees with similar name prefixes
- **Fix:** Validate against ParentCommitteeID from Committee API response

### 34. Schedule sub-panels not recognized as children (HCJ-Civil, HCJ-Criminal, etc.)
- **What broke:** House Courts of Justice, House Appropriations, House Finance, and House Labor and Commerce have Schedule API entries with hyphen-suffixed names ("House Courts of Justice-Civil", "House Appropriations - Health and Human Resources Subcommittee") that carry concrete times. The parent entries have "Time TBA". ### 35. api_schedule_map overwrites concrete times with TBA on duplicate entries
- **What broke:** Multiple Schedule API entries can exist for the same date+committee. `api_schedule_map[map_key] = {...}` overwrites unconditionally, so a later entry with "Time TBA" kills an earlier entry with a concrete time.
- **How it was caught:** Investigation of how duplicate entries are ordered in the API response.

### 36. Subcommittee vote refids (H14003V...) not parsed by resolve_committee_from_refid
- **What broke:** The vote regex `r'^([HS])(\d{1,2})V\d+'` only matched parent vote refids like `H14V2610034`. Subcommittee vote refids like `H14003V2610048` (parent code H14 + subcommittee suffix 003 + V + vote ID) have 3 extra digits before the V, which the regex didn't allow. Result: 1,637 subcommittee refids returned `(None, None)`. Without a refid match, actions fell to lexicon (which also fails for "H Subcommittee recommends..." since no committee name appears in the text) → Memory Anchor → often wrong committee → Journal Entry → Ledger.
- **How it was caught:** Post-PR#16 X-Ray showed 453 Ledger meeting bugs, all COMMITTEE_DRIFT tagged with subcommittee actions. Sample refids like `H24001V2612630` confirmed the pattern.
- **Data:** 1,637 subcommittee refids missed across 14 House committees. Top: H02 (245), H14 (203), H08 (179), H24 (159).
- **Fix:** Expanded regex to `r'^([HS])(\d{1,2}?)(?:\d{3})?V\d+'` — non-greedy `\d{1,2}?` captures the parent code (1-2 digits), optional `(?:\d{3})?` matches the strictly 3-digit subcommittee suffix. Non-greedy is critical: greedy `\d{1,2}` would consume a digit from the subcommittee suffix on 1-digit parent codes (e.g., S2001V → S20 instead of S2). Verified: zero false positives against all non-committee refid formats.
- **Lesson:** When an ID format has structural components (parent + subcommittee + vote), the regex must account for ALL components, not just the most common pattern. Test against the full range of real data, not just a few examples. When consecutive numeric fields have variable width, greedy quantifiers are dangerous — always test with the minimum-length variant of each field.

### 37. "Prefiled and ordered printed; Offered..." misclassified as meeting action
- **What broke:** X-Ray `MEETING_ACTION_PATTERNS` contains the substring "offered" to catch legitimate committee/floor amendment offerings ("H House committee offered"). Query of HISTORY.CSV showed 3,682 total "offered" rows in session 261: 2,042 "Prefiled and ordered printed" (admin), 698 "H House subcommittee offered" (meeting), 526 "S Senate committee offered" (meeting), 184 "H House committee offered" (meeting), rest misc. The prefiled chunk is the dominant noise source.
- **Fix:** Added `"prefiled and ordered printed"` to `ADMIN_OVERRIDE_PATTERNS` in both `pages/ray2.py` and `calendar_xray.py`. Override is checked before `MEETING_ACTION_PATTERNS`, so prefiled rows now classify as administrative. Legitimate committee/subcommittee amendment offerings are unaffected (no "prefiled" substring).
- **Scope note:** This is a classification-hygiene fix. It corrects the meeting/admin denominator in X-Ray but does not by itself fix the ~41 genuine committee-amendment offerings that are in Ledger Updates due to missing committee convene times. That investigation continues.
- **Lesson:** Substring-based classification must be audited against real phrase frequency, not just the token meaning. "offered" as a bare word is a meeting verb; "prefiled and ordered printed" is a clerk phrase that happens to contain it. The specificity-wins override pattern (ADMIN_OVERRIDE_PATTERNS) is the right place for these exceptions.

### 42. PR-C3 LegislationEvent fallback: N+1 fetch (no per-cycle response cache)
- **What broke:** PR #30 merged 2026-04-25 ([[log#2026-04-25-pr--pr-c3-round-2--pr-30-merged-and-reverted-same-day]]). On the very next 15-min cycle the GitHub Actions worker hung 11+ min vs normal ~2 min and was manually canceled. Reverted on main as commit `246cba5`.

Telemetry from inside the cycle was unavailable — the cycle never finished writing its metrics row, so X-Ray showed nothing.
- **Root cause:** `_resolve_via_legislation_event_api` cached the `LegislationID` lookup (the bill-number → ID hop) per (bill, session) but did NOT cache the second HTTP call — `GetPublicLegislationEventHistoryListAsync`. The endpoint returns the bill's whole event history in one shot, so a *single* fetch covers every action_date for that bill. Yet every `journal_default` row in HISTORY.CSV that hit the gate triggered a fresh fetch. With ~3,000 unique bills and ~10,000+ journal_default rows across the full session window, that's thousands of redundant HTTP calls. Combined with `urllib3.Retry(total=4, backoff_factor=2)` on 429s, LIS WAF rate-limiting cascaded into 40s+ stalls per affected request — the cycle's wall-clock blew past the 15-min Actions schedule.
- **Audit hole that let this through:** Pre-merge testing exercised matcher correctness (4 Class-1 bug cases + HB1 multi-event + abstain safety nets, 11/11 passing) but did NOT exercise the gate's selectivity at session scale or the per-cycle HTTP-call count. The reviewer playbook for new fallback paths needs a **candidate-set sizing check** — for any new conditional that fires HTTP, count `n_eligible_rows` × `expected_calls_per_row` against the session window before merge. The matcher was correct in isolation; correctness in isolation is not correctness in production.
- **Fix:** PR-C3.1 (PR #31) adds `_legislation_event_cache` per-cycle, mirroring `_legislation_id_cache`. Keys are `(bill_num, session_code_5d)`. Successful fetch stores the events list; any failure path (network exception, non-200, parse error, non-dict shape) stores `[]` to negative-cache and suppress retry storms within the cycle. Categorized `push_alert` with `dedup_key` still fires on miss so the failure remains visible. Two new regression tests prove cache reuse and negative-cache (`test_pr_c31_event_cache_prevents_refetch`, `test_pr_c31_negative_cache_suppresses_retry_on_failure`).
- **Lesson:** When a fallback adds a new HTTP call inside a row-by-row loop, it is NOT a fallback — it is a multiplicative cost. The unit of caching must match the unit the source returns. Here the LIS endpoint's response unit is "the bill's whole history" but the worker's call unit was "each row." Whenever those don't match, the response MUST be cached at the source's natural granularity, not the consumer's loop granularity. Add this to the pre-push audit when any new fallback fires HTTP from inside a loop.

### 44. Revert-of-merge resolved via merge with `-s ours` (not `-X ours`, not `git revert <revert>`)
- **What broke:** PR-C3.1 was branched from the PR-C3 tip (`f5745c4`) to preserve a single review surface. After main reverted PR #30 (commit `246cba5`), GitHub showed PR #31 as conflicted. Two attempts to clear the conflict each had a non-obvious failure mode before the third worked.

- **Root cause:** This is the canonical "revert-of-faulty-merge" pattern documented in `git-scm.com/docs/howto/revert-a-faulty-merge`. Merge-base of branch and main was `f5745c4` (because main once contained PR-C3 via merge `4d398ac`). From base, main's diff is "delete PR-C3 lines" and branch's diff is "keep them, with PR-C3.1 enhancements". Both sides modified the same lines from the base, in opposite directions — true conflict.
- **Failed attempt 1: `git revert 246cba5` on the branch.** Conflicts resolved by taking HEAD ("ours") and the result was a zero-diff commit — `git status` reported "nothing added to commit". The branch HEAD already contained everything `246cba5` removed (plus the PR-C3.1 enhancements), so the revert tried to re-add content that was already there. An empty commit on the branch tip would not have changed file content on either side, leaving GitHub's three-way merge state — and conflict — unchanged. Aborted.
- **Failed attempt 2: `git merge -X ours --no-ff origin/main`.** The `-X ours` *strategy-option* only resolves textual conflicts in our favor. For non-conflict regions where "ours" hadn't diverged from base but "theirs" had (the revert deleted lines, ours had no diff vs base for those lines), git auto-applied "theirs" change as a clean non-conflict — silently un-applying module-level constants like `LEGISLATION_EVENT_HEADERS` that the resolver depended on. Caught by tests dropping from 13/13 to 5/13 with `NameError: name 'LEGISLATION_EVENT_HEADERS' is not defined` traced via `sys.settrace`. Aborted.
- **Working fix: `git merge -s ours --no-ff origin/main`** (commit `a2bb618`). The `-s ours` *strategy* (not strategy-option) discards "theirs" tree entirely while still recording main as a merge parent. Branch's tree stayed byte-identical to pre-merge (13/13 still passing); merge-base of branch and main shifted to `246cba5`; subsequent `branch → main` merge has zero divergence; no force-push, no history rewrite.
- **Lesson:** When a feature branch built on the pre-revert state needs to merge into a main that has reverted those changes, the right operation is `git merge -s ours` on the branch — NOT `git revert <the-revert>` (zero-diff no-op when ours already has the content), and NOT `git merge -X ours` (silent corruption on non-conflict deletions). The strategy form is for "I want my tree, but I want main in my history so the conflict goes away." The strategy-*option* form is for "merge normally, but tiebreak conflicts toward ours" — different semantics, dangerous default for revert-of-merge. **Process check:** after any merge with non-trivial conflict resolution, RUN THE TESTS before pushing. The `-X ours` corruption was caught only because tests fired before the push button was reached. If we'd pushed and let CI run, we'd have polluted PR #31's history with a broken commit and probably triggered another bot review cycle.

### 47. Queue-with-cap requires explicit overflow handling — items beyond the cap don't disappear, they continue through the system (PR-C7 review fix)
- **What broke:** PR-C7's first commit (`70f14f8`) introduced a refresh queue capped at `LEGEVENT_FETCHES_PER_CYCLE = 500` for hydrating the cross-cycle LegEvent cache. The queue building was correct (Tier A → B → C, cap enforced, overflow telemetry in place). But the row-loop integration assumed *implicitly* that "any bill that needs fetching is in the cache after hydration." That assumption broke for **Tier A overflow bills** — bills that needed hydration but exceeded the 500 cap (queued for next cycle). When a row from one of those bills reached the journal_default LegEvent fallback at `calendar_worker.py:3110`, the resolver's existing PR-C3.1 cache check `if cache_key in legislation_event_cache:` was False (no entry), and the resolver fell into its network-fetch path. **The 500-fetch cap was bypassed.** Worst case: cold-start cycle 1 with 1,500 Tier A overflow bills could fire 1,500 ad-hoc fetches from the row loop, recreating the [[#42|PR-C3 hang]] vector this entire PR was designed to eliminate.
- **How it was caught:** **Codex P1** and **Gemini critical** flagged the same issue independently in PR review on commit `70f14f8`. Both correctly identified that overflow bills bypass the cap. Two-bot agreement on the same flaw is a strong signal that the issue is real and not a false positive.
- **Fix:** PR-C7 review fix commit `45c72b5` adds a "negative-cache seed" loop AFTER the hydration phase, BEFORE the row iteration. For every candidate bill that did NOT make the queue (Tier A overflow, OR skipped on terminal/fresh), seed both:
    `_legislation_id_cache[(bill, session_5d)] = ""` — falsy value; resolver bails at `if not legislation_id` BEFORE any network fetch
    `_legislation_event_cache[(bill, session_5d)] = []` — empty list; resolver bails at `if not matching` (defense in depth)
  The resolver short-circuits without making any HTTP request. The row loop is now strictly cache-lookup-only regardless of which tier a bill is in, or whether it was hydrated this cycle. New telemetry counter `legevent_overflow_no_fetch` tracks how many bills were seeded with negative cache so the operator can see "this cycle suppressed N row-loop fetches that the prior PR-C7 design would have made."
- **Root cause (process-side):** I framed PR-C7 around the hydration phase ("the row loop is now lookup-only because hydration pre-populates everything") and didn't trace what happens to items that don't make the cap. The queue's cap enforcement was correct in the queue-building code, but the row-loop integration silently assumed hydration was complete. **The bug lived at the seam between two correctly-implemented components.**
- **Lesson:** **When introducing a queue with a per-cycle cap, items that exceed the cap do NOT disappear from the broader system — they continue through whatever logic consumes the queue's output. Explicit handling is mandatory.** Three patterns for handling overflow:
  1. **Negative cache (preferred when downstream consumer already has a "key absent" semantics):** seed the consumer's data structure with a value that signals "intentionally not fetched this cycle." Downstream calls short-circuit cleanly. (PR-C7's fix.)
  2. **Bypass branch:** add an explicit check at the consumer site that skips the consumer's expensive path if the item wasn't queued. Less elegant; couples consumer to queue.
  3. **Bounded-blocking:** make the consumer wait for the queue to drain. Defeats the point of the cap. Don't use.
  The first two are valid; pick based on which side has cleaner semantics. **Process upgrade:** when implementing a queue-with-cap pattern, the pre-push audit MUST trace one explicit overflow item end-to-end through the system. If the overflow item triggers any expensive operation downstream (network fetch, DB write, etc.), the cap is theoretical. Bot review caught this; the next instance might not.

### 50. Function-scope import shadows module-level binding for the entire function — PR-C7 cold-start brick (PR-C7.0.1 hotfix)
- **What broke:** PR-C7 merged at `c917d6de` 2026-05-05T00:01:55Z. The very first cycle on post-merge main (run 25350329090, `workflow_dispatch` at 2026-05-05T00:02:24Z, ~30s after merge) crashed with `UnboundLocalError: local variable 'timezone' referenced before assignment` at `calendar_worker.py:1893` inside `run_calendar_update()`. Worker bricked — every 15-min cycle would have failed identically until fixed. Last green cycle was 2026-05-04T23:35:53Z (run 25349432088 on pre-merge `30391238`).
- **Root cause:** PR-C7 added `from datetime import timezone` at `calendar_worker.py:2793` inside the LegEvent recovery block of `run_calendar_update()`. Python's scoping rule treats *any* name assignment (including `from X import Y`) as making the name local for the **entire enclosing function**, regardless of where in the function it appears. So the earlier references at lines 1893 and 1906 — which had been resolving to the module-level `from datetime import datetime, timedelta, timezone` at line 12 — suddenly became local references that hadn't been bound yet at the point of access. The module-level `timezone` was already in scope; the local re-import was redundant *and* poisonous.
- **How it was caught:** worker GitHub Actions run failure log immediately after merge. The cycle could not even reach the LegEvent block — it died at `_cycle_start_utc = datetime.now(timezone.utc)` at line 1893, very early in `run_calendar_update()`. Detection lag: ~30 seconds (next cycle after merge). Fix lag: ~5 minutes (PR #42 opened on commit `efe1a90`, one-line deletion).
- **How it escaped the 9-point pre-push audit:**
  1. Point 8 (Import Resolution from Subpage) checks `pages/*.py` import paths — function-scope import shadowing inside `calendar_worker.py` itself was not in scope.
  2. Parse-cleanliness was confirmed (`python -m py_compile`) but execution-cleanliness on the actual entry path was not. The bug ONLY surfaces at runtime when the function is invoked.
  3. The redundant import was syntactically harmless and visually plausible — a maintainer reviewing the diff sees `from datetime import timezone` next to `datetime.now(timezone.utc)` and assumes it's needed for that line.
- **Lesson:** **Never write a redundant `from X import Y` inside a function when `Y` is already imported at module level.** The redundancy isn't merely stylistic — it changes the scope of *every reference to `Y`* in the function, retroactively making the function local-bind. Even if today's references all fall after the local import, tomorrow's refactor that adds an earlier reference will break with `UnboundLocalError`. **Audit upgrade:** add Point 10 to the 9-point pre-push audit — *Function-Scope Shadow Check.* For any function containing a local `from X import Y` or `Y = ...` assignment, grep the function body for all references to `Y` and confirm every reference appears textually after the local binding. Better still: if `Y` is already at module level, just delete the local binding. **Process upgrade:** parse-clean is necessary but not sufficient. A 60-second pre-merge dry-run (worker invoked with `IS_DRY_RUN=true` env var, no sheet writes) would have caught this and any other cold-path runtime error. PR-C7's 558-line diff merited that step. Add to the workflow: post-CI, pre-merge, fire a `workflow_dispatch` dry-run on the head commit and confirm it reaches steady-state log lines before merging.

The specification was wrong because it was anchored to a transient value, not to a structural property.
- **How it was caught:** owner pattern-matched on the gap counter climbing past 24 hours and asked "stale data is unacceptable in a live tracking environment" — a directive that forced the calibration question to the surface. Reserve absolute thresholds for genuine catastrophes (the 500 floor here) where the floor IS structurally fixed (cardinality-of-bills × per-bill-row-cap × something). Treat any cycle-stable breaker trip as a CRITICAL calibration bug, not a transient. **Process upgrade:** breaker-carry-forward already surfaces the trip as a SYSTEM_ALERT one cycle later. Add a "trip-streak counter" — N consecutive trips without a successful cycle in between is a different failure mode than a single trip and should escalate (CRITICAL severity, distinct dedup_key) so monitors can distinguish "transient anomaly" from "stuck breaker." **Cross-reference:** this is the same shape of failure as #48 ("when a metric jumps suddenly at scale, sample-verify the metric's definition before scoping a fix") — both are "the metric's behavior changed, the static interpretation didn't follow." #48 was about diagnosis (we measured wrong); #53 is about action (we acted on a stale threshold). **Stale data is unacceptable in a live tracking environment** — the breaker exists to protect against bad writes, but a breaker that trips on healthy operation is itself the bad outcome.
- **Bot review fold-in (Codex P2, PR #45 commit `af4aa7e`):** the initial fix keyed delta-check activation on `last_known_good_meeting_unsourced > 0`, which silently conflated two semantically distinct states: (a) Y2 absent / unreadable / malformed → no trusted baseline, bypass delta-check (correct behavior), AND (b) Y2 = "0" → valid baseline of zero, delta-check should remain ACTIVE. ### 61. `set.discard()` on a Counter-shaped key loses multiplicity — CONVENE GAP report underreported mixed-recovery floor days (PR-C7.1c Codex P2 + Gemini medium fold-in, 2026-06-02)

- **Context:** PR-C7.1c introduced LegEvent floor recovery. Each floor miss incremented `_floor_miss += 1` and `_floor_miss_dates.add(combo)` where combo is the `f"{date}_{chamber}"` key. On a successful recovery, the code did `_floor_miss -= 1; _floor_miss_dates.discard(combo)`.
- **What broke:** the global `_floor_miss` counter correctly reflected unrecovered misses, but `_floor_miss_dates` was a `set` — same combo can be added multiple times (multiple rows on the same date/chamber), but `set.discard(...)` removed the key entirely whether 1 or 5 misses had used it. - **Fix:** switched `_floor_miss_dates` to `collections.Counter`. Increment-on-miss is `[combo] += 1`; decrement-on-recovery is `[combo] -= 1; if [combo] <= 0: del [combo]`. - **Generalization:** if an item can be added multiple times to a collection AND you ever decrement / remove instances, `set` is the wrong choice — multiplicity is what you need to track. Use `Counter` (preferred — built for this) or `defaultdict(int)`. **Audit hook:** when a `set` is updated inside a loop where the same key can repeat AND there's a corresponding `discard` / `remove` path, sanity check: is the discard supposed to remove ONE occurrence or ALL of them? ### 64. Two matchers, one contract, only one enforced it: `_route_for_row` accepted 0-overlap matches → admin rows inherited a coincident meeting's route (PR-C7.1i, 2026-06-03)

- **Context:** post-hydration (97.8%) the X-Ray Section-9 route-aware count was 266, not the projected ~3. Tracing the residue: ~106 of the 123 `route==meeting`+no-time rows were *administrative* outcomes — "Placed on X Agenda", "Rereferred to Finance" — that the structural router had routed to **meeting**.
- **Root cause (confirmed on SB41):** on 2026-01-15 SB41 had TWO HISTORY actions — "Reported from Transportation (14-Y 0-N)" (a committee vote → meeting; the only cached LegislationEvent that day) and "Rereferred to Finance and Appropriations" (a clerk routing → admin). `_route_for_row` filters cached events to the row's `(date, chamber)` then `best = max(cands, key=token_overlap)` and returns `_route_event(best).route` — **without checking that the overlap is non-zero.** "Rereferred…Finance" shares zero tokens with "Reported…Transportation", but it was the only same-date event, so the rereferral row inherited the report's `meeting` verdict.
- **The tell:** the sibling matcher `_find_legevent_time_in_cache` (the TIME path) ALREADY had the guard — `best_score = scored[0][0]; if best_score == 0: return None`. So the two matchers, which share the same "match the outcome to its own event" contract, disagreed: the time matcher rejected coincidental same-date matches; the route matcher accepted them. The time path was therefore correct (no wrong times), but the route path manufactured ~106 false-positive meetings.

A 0-overlap row falls back to the X-Ray's text classifier, which puts "Rereferred"/"Placed on" in `ADMINISTRATIVE_PATTERNS` → admin. Unit-tested: SB41 case → blank (not meeting); real-overlap report → meeting (preserved); overlapping admin → admin (preserved).

Same family as #62/#63 (proxy-vs-actual): "the best candidate" is not the same as "a candidate that actually matches."

### 66. `str(None)` persisted a JSON-null API field as the literal string `"None"`; on cache RELOAD that truthy sentinel made the chamber filter exclude every Governor event → blank route → 114 Section-9 rows. - **Context:** post-hydration Section 9 sat at 210 with the single largest residue being **114 Governor rows** (`Governor's Recommendation`, `Governor's recommendation received by Senate/House`) carrying a **blank** `LegEventRoute`. A local `_route_for_row` reproduction insisted those same rows should route **admin** (ActorType=Governor). The repro and production flatly disagreed.
- **Root cause (raw-bytes probe, not guess):** the LIS `LegislationEvent` API returns JSON `null` (Python `None`) for a Governor event's `ChamberCode`. The persist path serialized it with `str(e.get("ChamberCode", ""))` — but the `""` default only fires when the **key is missing**, not when the **value is None**, so `str(None)` wrote the literal string **`"None"`** into the sheet. Fresh-from-API events keep real `None`, which the chamber filter's `e.get("ChamberCode") or ""` correctly collapses to `""` (None is falsy) → they route fine. Cache-RELOADED events carry the **truthy** string `"None"`, so the same filter computes `ev_chamber="NONE"`, sees `"NONE" != "S"`, and **excludes the event as a non-matching chamber** → `_route_for_row` finds no candidate → returns `""` (blank). The bug was therefore invisible until a bill had been *evicted from memory and reloaded* — exactly the steady state after full hydration.
- **Why the repro hid it (the meta-lesson, same family as #62/#63):** the reproduction read the sheet with `pandas.read_csv`, which **auto-converts the string `"None"` to `NaN`** → the trace saw `""` → not excluded → "should be admin." `gspread.get_all_values` (the production reader) returns the raw string `"None"` → excluded. **The validation tool's parser silently healed the very corruption the production parser chokes on.** Confirmed by reading the raw gviz CSV bytes directly (`ChamberCode='None'`, not empty). *Always reproduce with the production reader, or with raw bytes — never a parser that normalizes differently.*
- **Fix:** a single `_clean_legevent_cell(v)` helper that collapses `None` and the stringified null sentinels (`"none"/"null"/"nan"`, case-insensitive) to `""`, applied to every nullable structural field (`ChamberCode`, `EventCode`, `ReferenceType`, `ActorType`, `Status`, `EventDate`) on **both** persist (stop writing `"None"`) and load (heal the existing corrupted rows on the very next cycle, no re-persist wait). `VoteTally` was already guarded; `Description` is left raw (free text may legitimately contain "None"). Zero new imports, zero per-state config. With it, cache-loaded and fresh-API events route **identically** — the Governor rows now route admin → Ledger Updates (a Governor's executive action is not a legislative *meeting*, so it correctly leaves Section 9 entirely).
- **Generalization (audit point #15, Sentinel-Value Collision):** **`str(x)` on a nullable field is a latent sentinel-collision bug** — `None`, the JSON `null`, and the *string* `"None"` must never be allowed to mean three different things across a serialize→deserialize boundary. Any field that can be JSON-null and is later compared/filtered as a string must be normalized at BOTH ends of persistence. **Audit hook:** grep persist code for `str(e.get(` / `str(row[` on API-sourced nullable fields; each one is a `"None"`-string risk. And: a round-trip is only proven correct when the **reader used in production** is the reader used in the test.

When a derived row (a split secondary, a procedural floor action) can't be timed, ask what meeting the SOURCE says it happened in — the answer is a published field away. Same spirit as #67/#69: consume LIS's structure; the data is the dictionary.

- **Regression + fix (PR-C7.1p.1, same day):** the first cut shipped a real bug — the persisted LegEvent cache never stored `CommitteeName`, so the recovery read `None` for every CACHED event and timed ALL of them as floor actions → SJ209 (a committee report) got the 10:00 AM convene time instead of staying timeless. The verification CAUGHT it (Section 9 hit 3, but SJ209's row showed a convene time it shouldn't have). Fix: persist `CommitteeName` with a 3-state sentinel — a name (committee → meeting time or None, never convene), `None`/"" (floor → convene), and `"?"` for a pre-column cache row (UNKNOWN → refuse to recover until the value back-fills on the next fetch). **Meta-lesson: a recovery that joins on a field must persist that field — reading it only from the fresh-API path silently degrades to a wrong default the moment the row comes from cache (same family as #66, the `"None"`-string cache bug). And: ALWAYS verify the produced ROW, not just the count — Section 9 dropping to 3 looked like a win until the actual cell showed a fabricated time.**

### 72. The last "timeless" rows weren't timeless — they were `api_schedule` rows stuck at "Time TBA" because the worker attributed a FLOOR/subcommittee action to a committee LIS published with an empty time; the LegEvent's own CommitteeName/timestamp had the answer (PR-C7.1q, 2026-06-04)

- **Context:** owner: "evaluate the 4 — can any known solution be applied?" Pulling each one's LegEvent showed 3 of 4 were NOT genuinely timeless: HB447/HB919 "Continued pursuant to Rule 22" are `CommitteeName=None` (FLOOR actions) the worker mis-filed under "House Courts of Justice" (empty schedule time); SB834 is an `H1088` subcommittee recommendation with a real **14:00** timestamp mis-filed under empty-time "House Appropriations". The recovery (#71) already knew how to fix this — but only fired for `journal_default` rows; these had matched a committee and were sitting at `api_schedule`/`Time TBA`.
- **Fix:** run `_recover_time_via_legevent_committee` ALSO for an `api_schedule` row whose matched time is non-concrete (TBA). It re-attributes on the LegEvent's authoritative `CommitteeName`: floor (None) → chamber convene time; a scheduled committee → that time; else the event's own timestamp via a new `_plausible_meeting_time` (last-resort, hours-gated). Blast radius is the 484 TBA rows, but it only CHANGES a row when a concrete signal exists, so a genuinely-timeless meeting stays TBA. Section 9 4 → 1.
- **The one assumption (Standard #1):** `_plausible_meeting_time` accepts a LegEvent timestamp only in [07:00, 23:00] — LIS stamps non-meeting events with 00:00/04:00/05:00 document-batch artifacts, and a meeting actually held lands in business/evening hours. It is a LAST resort (committee unscheduled AND not a floor action) and bounded so an artifact can't leak through. If a real committee ever met before 7 AM it would be skipped (stays TBA, never wrong) — the safe failure direction.
- **Generalization:** **"api_schedule but TBA" is the same class as "no schedule match" — a JOIN on the wrong key (text committee) when the right key (LegEvent CommitteeName) was a field away.** Re-extend any recovery that keys on the upstream's structured attribution to ALL non-concrete outcomes, not just the fully-unmatched ones. Only SJ209 is now truly irreducible (LIS published no meeting for it at all).

### 73. Stress-test pass (tomorrow / 6 months / 2 years): the annual multi-session cache overflow would have re-triggered the #62 truncation in 2027; plus a LIS field-rename canary, a sheet-open retry (PR-C7.1s, 2026-06-04)

- **Context:** owner: "imagine what causes it to fail tomorrow, in 6 months, in 2 years." Adversarial failure-mode audit (full matrix: [[architecture/stress_test_failure_modes]]). Three findings fixed in this pass; the rest triaged.
- **HIGH (6 months) — multi-session cache overflow:** the LegEvent cache is keyed `(bill, session)` and re-persisted IN FULL each cycle, but never pruned old sessions. A 2027 run would load 2026's ~65k events AND hydrate 2027's ~65k → ~130k rows > the 120k tab cap → **silent truncation — literally the #62 bug, recurring every January**. The original #62 fix raised the cap; it didn't address accumulation. Fix: `_load_legevent_cache(active_session=...)` loads only the active session, so the tab self-prunes the prior session on rollover (the next full persist clears the stale rows).
- **HIGH (2 years) — LIS field-rename canary (Y2):** the entire structural architecture keys off specific event fields (`CommitteeName`, `VoteTally`, `ReferenceType`, …). A silent upstream rename/removal would break routing with NO error — the deepest single risk of a structure-consuming design. There was a `validate_status_grouping` canary for new Status *values* but none for renamed/removed *fields*. Fix: assert `_EXPECTED_EVENT_KEYS` against each fetched event; CRITICAL alert on drift.
- **MED (tomorrow) — sheet-open 503:** a transient Google Sheets 503 on `open_by_key` failed the whole cycle (observed this session). Fix: retry 3× with backoff.
- **Generalization:** **"we fixed the symptom" ≠ "we fixed the class."** #62 raised a cap to fit ONE session; the failure class (a per-session store re-persisted in full, unbounded across sessions) only shows up at the NEXT session boundary — a year away, invisible in same-session testing. Stress-testing across TIME HORIZONS (not just current data) is how you catch the bug that's dormant until the calendar flips. And: a structural design that consumes an upstream's field names needs a schema canary as much as a value-vocabulary canary — the field IS the contract.

### 74. The 05:00 doc-batch artifact slipped the router's `_NON_MEETING_TIMES` blocklist while the recovery's `[07:00,23:00]` window excluded it — two definitions of "real meeting time" disagreed, so Rule-22 continuances routed `meeting` and surfaced timeless (PR-C7.1t, 2026-06-04)

- **Context:** owner: "just go until you finish all those items, then stress-test." On cold-start re-verification AFTER the backfill burst + #87 landed, the live X-Ray Section 9 measured **6**, not the **1** that #72 had *projected*. First lesson is procedural: **#72's "4 → 1" was never actually measured — the verifying burst (run 26976660374) checked out the PR #84 commit, an hour BEFORE #87 merged, so it ran the pre-recovery code.** A PR that claims a metric delta must be verified on a run that provably CONTAINS that PR's commit (`gh run view --json headSha` vs the merge SHA). Measuring against a stale worker is how a projection masquerades as a result — the exact "verify the row, not the count" family (#62/#68/#82), one level up: verify the CODE, not just the number.
- **The real measurement:** a faithful reproduction of ray2.py's `bug_count = len(mt_without)` against the live Sheet (route-aware `classify_action(Outcome, LegEventRoute)` + `normalize_time ∈ PLACEHOLDER_TIMES`) gave 6; a fresh worker cycle on `main` (with #87) brought it to **4** (SB834 → 2:00 PM via the `H1088` 14:00 voice vote; HB919 → 2:00 PM via its 14:00 rerefer event). Remaining 4: HB447, HB438, SJ209, HB246 — each pulled from LIS to find its ACTUAL published event.
- **The structural bug (HB447/HB919-class):** "Continued pursuant to House Rule 22 to 2027" (`EventCode H0840`) is a batch end-of-session disposition — every bill left in a House committee gets it, stamped `05:00:00` with no vote tally. By the project's own rule that is administrative → Ledger, no time. But it routed `meeting`. Root cause: `structural_router._has_meeting_time` used a BLOCKLIST `_NON_MEETING_TIMES = {00:00, 04:00}` that **did not include 05:00**, so `_has_meeting_time("…T05:00:00") == True` → H0840 looked "timed" → disqualified from the ministerial law (#67) → routed `meeting` → no renderable time (the recovery's `_plausible_meeting_time` uses `[07:00,23:00]`, which DOES exclude 05:00). **Two inconsistent definitions of "a real meeting wall-clock time" — the router's blocklist and the recovery's window — disagreeing on 05:00 was the whole bug.**
- **Fix:** replace the blocklist with the SAME business-hours window `[MEETING_HOUR_MIN=7, MEETING_HOUR_MAX=23]`, defined ONCE in `structural_router` and imported by `calendar_worker._plausible_meeting_time`. A bounded range, not an artifact blocklist, ends the whack-a-mole and cannot silently drift past a newly-observed batch hour. H0840 (and the Enrolled/Bill-text `H5601/H5610/S5601/S5610` codes that also carry 05:00 stamps) now classify ministerial → admin → drop out of Section 9 correctly.
- **Validation (Standard #7, measured not asserted):** sampled 117 bills / 300 EventCodes. Every code the new window NEWLY captures is clerical (Enrolled, Bill text, Signed by Speaker/President, Placed on Calendar, communicated to Governor, Governor deadlines, Rule-22 continuance); NOT ONE deliberative action. Every committee/floor action that lands at 00:00 (e.g. `S0805` "Reported from P&E (13-Y…)", `S1307`) carries a **vote tally** and is protected by the ministerial law's `not voted` clause regardless of time — confirmed: H0840 → ministerial, S0805 (voted) → NOT ministerial.
- **The honest residual (measured, not projected):** after this fix Section 9 = 3 — and only ONE is irreducible: **SJ209** (`S0805` "Reported from P&E", voted 13-Y on 3/10, but LIS published NO P&E meeting that day — `api_2026-03-10` has only caucuses + Senate Convenes; the time exists nowhere). The other two are deeper, separately-tracked: **HB438** "Rereferred to Finance" is the admin half of a compound voted `S1307` "Reported from Courts of Justice AND rereferred" whose Senate committee meeting is itself absent from `api_2026-03-02` (no committees that date); **HB246** "Passed by for the day" is a Reconvened-Session (4/22) floor action that should anchor to `House Convenes 2026 Reconvened Session@12:00 PM` but the floor→convene recovery returned None. Neither is claimed fixed here — documenting root cause beats projecting a number.
- **Generalization:** **when two code paths each answer the same predicate ("is this a real meeting time?"), they must share ONE definition by value, or they WILL drift — and the drift is silent.** This bug was born the moment the router got a `{00:00,04:00}` blocklist while the recovery got a `[07:00,23:00]` window; the 05:00 artifact lived in the gap between them. Prefer a single shared constant over two "equivalent" literals. Same root class as the Pre-Push Audit's Sentinel-Value and Function-Scope-Shadow checks: one fact, one home.

### 75. The structural recovery was permanently starved on TERMINAL bills: their cache predates the CommitteeName column ("?"), the recovery refuses "?", and the refresh queue never re-fetches a terminal bill — so the "?" never back-fills (PR-C7.1u, 2026-06-04)

- **Context:** after the 05:00 ministerial fix (#74) the measured Section 9 held at **4** (HB447, HB438, SJ209, HB246), not the projected 3 — the fix correctly swept the COMMON clerical codes (Enrolled/Bill-text, +~900 events, 33→37 ministerial codes) but `H0840` "Continued pursuant to Rule 22" is too sparse in the cache to clear the ≥20 ministerial floor. Pulling each residual showed the time it needs ALREADY EXISTS: HB438's report sibling is timed **8:00 AM** (Senate Courts of Justice), HB246's 4/22 has **House Convenes Reconvened@12:00 PM**, HB447's H0840 is a floor action with a convene time. Yet `_recover_time_via_legevent_committee` returned None for all of them.
- **Root cause (a three-way structural deadlock):** (1) the recovery REFUSES a matched event whose persisted `CommitteeName == "?"` (the schema-incomplete sentinel — it can't tell a committee action from a floor one, the #71-regression guard). (2) These bills are **terminal** (passed + signed + Approved by Governor), and `_build_legevent_refresh_queue` SKIPS every `IsTerminal` bill (line 1704) — correct for a frozen-history bill, except (3) they were last hydrated in an EARLIER session, BEFORE the `CommitteeName` column existed (#82/PR #84), so their cached events carry `"?"`. Terminal-skip means that `"?"` **never back-fills — no number of cron cycles or backfill bursts touches them** (the burst skipped them too; the IsTerminal gate predates it). The recovery is permanently dead for the exact rows it was built to fix.
- **Fix:** in the refresh queue, a terminal bill whose cached events are schema-incomplete (`any CommitteeName == "?"`) is re-queued ONCE (Tier B) to migrate the column; the next persist writes the real `CommitteeName` and it returns to terminal-skip. Bounded (only "?" rows), deterministic (one fetch each), self-completing — the cache-side analogue of a schema migration. New `terminal_schema_backfill` counter in the metrics line for visibility (Standard #4). Once back-filled, the recovery fires same-cycle on the in-memory value: HB438 → Senate CoJ 8 AM, HB246 → House Reconvened convene 12 PM, HB447 → House convene (or `H0840` joins ministerial as more continued bills hydrate). SJ209 stays timeless (its committee, P&E, genuinely has no published 3/10 meeting).
- **Generalization:** **adding a column to a cached/persisted store is a MIGRATION, not a code change — any consumer that refuses the unmigrated sentinel must be paired with a path that re-materializes the old rows, or they rot forever.** The danger compounds when an orthogonal optimization (terminal-skip) means the natural refresh cycle never revisits them. Same family as #56 (stale narrower cache rows) and #71-regression (persist the field you join on): a recovery that joins on a column is only as live as the column's BACK-FILL guarantee. When you introduce a structural field mid-flight, ask "what re-fetches the rows that predate it?" — if the answer is "nothing, for some subset," that subset is silently excluded from every feature built on the field.

- **Correction (PR-C7.1v, same night — measured, not assumed):** PR-C7.1u guessed the skip was `IsTerminal`. The verifying run proved otherwise: `terminal_schema_backfill=0`, `skipped(terminal/fresh)=0/3645` — **every bill is `IsTerminal=FALSE`**, so the terminal-branch check was dead code. Reading the live `LegEvent_Events` tab directly (it's gviz-readable like Sheet1): **exactly 500 bills / 12,793 events still carry `CommitteeName="?"`** (the rest, 3,145 bills, migrated during the burst). These 500 are skipped as **"fresh"** — `persist bumps FetchedAtUTC without a re-fetch`, so an unmigrated bill looks perpetually within its 6h TTL and never re-qualifies. The recovery itself was **proven correct** by replicating it on FRESH API data (HB438→8:00 AM, HB246→12:00 PM, HB447→10:00 AM all resolve); the ONLY defect was the unmigrated cache. Real fix: detect the `"?"` column DIRECTLY and re-queue BEFORE the terminal AND TTL skips, so it migrates regardless of either. **Meta-lesson (again): don't reason about cache state — READ it. The "terminal" hypothesis was plausible and wrong; one direct read of the persisted tab replaced a guess with the exact 500-bill / 12,793-event scope. And a "freshness" signal that tracks last-PERSIST instead of last-FETCH will mask a stale row forever (separate latent bug, noted for follow-up).**
